# 05-05 — Confirmação idempotente e gravação tudo-ou-nada (lancamento + conta_a_pagar)

**Wave:** 5 | **Depends on:** 05-04 | **Autonomous:** true | **Frontmatter status:** planned

## Objective

Implementar `POST /api/importacoes/{id}/confirmar`: o usuário confirma quais itens de staging quer gravar (itens desmarcados são ignorados; categoria pode ser overridida). Grava em **transação tudo-ou-nada**: `RECEITA` → `lancamento` (tipo `ENTRADA`), `DESPESA_PAGA` → `lancamento` (tipo `SAIDA`), `A_PAGAR` → `conta_a_pagar` (categoria do tipo SAIDA) + `fatura_cartao` quando houver cabeçalho de fatura. Marca itens `IMPORTADO` com o id do lançamento/conta_a_pagar criado — confirmar duas vezes não duplica (idempotência).

## Requirements

IMP-09, IMP-10, IMP-11, IMP-12

## Decisions covered

D-02 (gravação só após confirmação explícita), D-07 (transação tudo-ou-nada + idempotência), D-08 (chave_dedupe evita duplicação), D-24 (mapeamento de tipos), D-10 (tenant do JWT), D-11 (A_PAGAR não altera saldo do dashboard — `lancamento.tipo` inalterado)

## Threat Model

| Ameaça | Severidade | Mitigação |
|--------|------------|-----------|
| Confirmação dupla duplicando lançamentos | Alta | Item de staging passa a `IMPORTADO` guardando id do gravado; segunda confirmação pula itens já `IMPORTADO` (idempotência) |
| Item de empresa B confirmado por empresa A | Alta | `ImportacaoItem` filtrado por `empresa_id` do token; repositório valida `empresa.id = :empresaId` |
| Falha na metade do lote deixando lançamentos parciais | Alta | `@Transactional` tudo-ou-nada: qualquer exceção faz rollback completo (padrão `LancamentoService.processarLote`) |
| `A_PAGAR` entrando no saldo do dashboard | Alta | `A_PAGAR` vai só para `conta_a_pagar`; `lancamento.tipo` continua `ENTRADA|SAIDA` (D-05/D-11) |

<action>
Criar DTO de confirmação e service de gravação:
- Record `ConfirmarItem { Long itemId; Boolean incluir; Long categoriaIdOverride; }` e record `ConfirmarRequest { List<ConfirmarItem> itens; }` (ou equivalente).
- `ImportacaoService.confirmar(Long importacaoId, ConfirmarRequest request, Long empresaId)` (@Transactional):
  - Busca `importacaoDocumento` por id, validando `empresaId` (senão 404).
  - Para cada item de staging da importação: se `incluir == false` ou item já `IMPORTADO` → pular (reportado como ignorado/duplicado).
  - `RECEITA` → `lancamentoRepository.save` com tipo `ENTRADA`, categoria do override ou mapeada, `origem`, `documentoId`, `chaveDedupe`.
  - `DESPESA_PAGA` → `lancamentoRepository.save` com tipo `SAIDA`, mesma lógica.
  - `A_PAGAR` → salvar `faturaCartao` (se ainda não existir para esse documento) + `contaAParagarRepository.save` (categoria tipo SAIDA, vencimento da parcela ou da fatura).
  - Marcar item `IMPORTADO`, gravar `lancamentoId`/`contaAPagarId`.
  - Se qualquer linha falhar (categoria inválida, chave_dedupe duplicada, valor inválido) → exceção com índice da linha e rollback total (padrão `LinhaInvalidaException` com `indiceLinha`).
  - Marcar documento `CONFIRMADO`; devolver `{ importados, ignorados, duplicados, lancamentos }`.
- Reutilizar `LancamentoService.criar` lógica (validação monetária, integridade categoria×tipo) via chamada direta ou duplicação controlada — mas sem gravar `empresa_id` do body.
</action>
<acceptance_criteria>
- `ImportacaoService.confirmar` existe, `@Transactional`, compila

- Erro em qualquer linha → rollback completo (nenhum lançamento gravado) + resposta com índice da linha (estilo `LinhaInvalidaException`)
- `mvnw -q test -Dtest='*Importacao*Confirm*,*Lancamento*Lote*'` passa (regressão do lote existente + novo)
