# 06-03 — Onboarding transacional, convites e gestão de usuários (Fase 2)

**Wave:** 3 | **Depends on:** 06-02 | **Autonomous:** true | **Fase:** F2

## Objective
Implementar o cadastro self-service de empresas (empresa + ADMIN + categorias padrão em uma transação), o ciclo de convites single-use e os endpoints públicos/ADMIN da seção 5, sem expor nenhum dado financeiro.

## Requirements
GROW-01, GROW-02, AUTH-02, AUTH-05 · **MT-02**

## Decisions covered
D-02 (onboarding transacional), D-04 (ADMIN só contas), D-05 (e-mail global único), D-07 (fluxo de convite), D-10 (convite hash/single-use/expira), D-12 (exceção pré-auth), D-18 (contratos de endpoint), D-24 (aceite F2).

## Threat Model
| Ameaça | Severidade | Mitigação |
|--------|------------|-----------|
| Cadastro cria empresa/usuário mas falha nas categorias → tenant órfão | Alta | `@Transactional` em `TenantOnboardingService` + teste de rollback forçado |
| Enumeração de e-mails no cadastro | Alta | Erro genérico 400 (mesma mensagem para e-mail existente), sem distinção |
| Convite reutilizado / expirado / usado por outro e-mail | Alta | `token_hash`, `expira_em`, `usado_em`, checagem de igualdade de e-mail — todos testados |
| ADMIN acessar dados financeiros via `/api/usuarios/**` | Alta | DTOs de conta apenas; nenhum repository financeiro injetado no controller de usuários |
| `empresa_id`/`usuario_id` injetados no body pré-auth | Alta | Endpoints derivam empresa do estado servidor; DTOs não têm esses campos |

## Risk Notes
- **Rollback real:** usar Testcontainers; mocks de repositório provam a lógica `@Transactional`, mas o teste de integração é o que garante rollback no banco.
- **Convite e Google (D-07):** o endpoint `/api/auth/google` só entra em 06-05 porque depende do validador de ID token; a intenção `CONVITE` é implementada la, reutilizando `ConviteService.aceitar`.
- **Role em String:** `JwtService` e `SecurityConfig` ainda leem `String` — a validação contra `Role` (D-15) entra em 06-04.
