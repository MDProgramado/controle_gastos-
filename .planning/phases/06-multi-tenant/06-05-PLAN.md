# 06-05 — Google OAuth/OIDC e BFF com PKCE (Fase 4)

**Wave:** 5 | **Depends on:** 06-03, 06-04 | **Autonomous:** true | **Fase:** F4

## Objective
Permitir entrar/cadastrar com conta Google: o backend valida o ID token (`iss`, `aud`, `exp`, `email_verified`, `google_sub`) e emite **JWT próprio**; o BFF faz Authorization Code + PKCE com `state` em cookie httpOnly e nunca expõe tokens do Google ao navegador.

## Requirements
AUTH-01, AUTH-02, GROW-01, GROW-02 · **MT-04**

## Decisions covered
D-01 (Google OIDC, backend valida ID token e emite JWT próprio), D-05 (e-mail global único), D-06 (e-mail existente entra na empresa existente), D-07 (nova empresa ou convite), D-09 (`google_sub`, `email_verificado`), D-12 (pré-auth deriva empresa no servidor), D-19 (BFF PKCE, `state` httpOnly, sem token Google no browser), D-20 (rate limit + PKCE), D-24 (aceite F4).

## Threat Model
| Ameaça | Severidade | Mitigação |
|--------|------------|-----------|
| ID token com `aud` errado / expirado / `iss` falso aceito | Alta | Validação pela lib Google com `GOOGLE_CLIENT_ID` e `iss=https://accounts.google.com`; teste 401 negativo |
| `email_verified=false` usado para assumir identidade | Alta | Rejeitar 401; gravar `email_verificado` somente quando true |
| CSRF no callback OAuth | Alta | `state` aleatório em cookie httpOnly + comparação server-side; PKCE `code_verifier` |
| ID token/access token Google vazando para o browser como sessão | Alta | Sessão é apenas o JWT próprio no cookie `sess`; callback server-side troca o code |
| Enumeração de e-mail no fluxo Google | Média | E-mail existente entra na empresa existente (D-06), sem revelar detalhes |
| Força bruta em `/api/auth/google` e callback | Alta | Rate limit por IP + throttle no BFF (D-20) |
| Conta Google sem senha utilizável | Média | `senha_hash` BCrypt aleatório (D-09) — login por senha impossível |

**user_setup (human-required):** Google Cloud Console — criar OAuth Client (Web), configurar redirect URI `https://<web>/api/auth/google/callback`, obter `GOOGLE_CLIENT_ID` e `GOOGLE_CLIENT_SECRET`; registrar no Render (`sync:false`) e no Vercel (server-side). Ver `user_setup` no frontmatter do plano 06-07 para deploy.

## Risk Notes
- **Credenciais reais:** o time de execução precisa das env vars Google (ver `user_setup`); sem elas, os testes unitários de validação usam fixtures e o e2e de Google fica bloqueado — sinalizar, não simular token válido em produção.
- **PKCE:** `code_challenge` deve ser S256 do `code_verifier`; não usar `plain`.
- **Rate limit em memória:** insuficiente para múltiplas instâncias na Vercel — migrar para store compartilhado na Fase 6 (06-07).
