# 06-02 — Migration V9, domínio e repositórios multi-tenant (Fase 1)

**Wave:** 2 | **Depends on:** 06-01 | **Autonomous:** true | **Fase:** F1

## Objective
Criar o schema multi-tenant (migration imutável `V9`) e o domínio Java correspondente: colunas `google_sub`/`email_verificado`/`token_version` em `usuario`, tabela `usuario_convite`, enum `Role`, índices e repositórios com busca por empresa/usuário/google_sub.

## Requirements
GROW-01, AUTH-01, AUTH-03, AUTH-05, INF-01, INF-02 · **MT-01**

## Decisions covered
D-08 (V9, nunca editar V1..V8), D-09 (colunas em `usuario`; `senha_hash` continua NOT NULL), D-10 (`usuario_convite` com token hash, single-use, expirável), D-11 (índices), D-15 (enum `Role`), D-24 (aceite F1).

## Threat Model
| Ameaça | Severidade | Mitigação |
|--------|------------|-----------|
| Migration aplicada sobre schema existente com dados corrompe produção | Alta | Testar em banco limpo **e** em cópia do schema atual (teste de migração), sem editar V1..V8 |
| E-mail deixar de ser globalmente único | Alta | Manter `UNIQUE (email)`; `google_sub` é UNIQUE parcial adicional |
| Role arbitrária virar `ROLE_<qualquer>` | Alta | Enum `Role` com conversão estrita (usada em 06-03/06-04) |
| Token de convite vazar em texto claro no banco | Alta | Coluna `token_hash` (SHA-256); texto claro apenas no link |

## Risk Notes
- **V9 sobre dados existentes:** `ALTER TABLE` com DEFAULT em `BOOLEAN`/`INT` é seguro em Postgres moderno, mas o teste em cópia do schema é obrigatório (D-24/F1).
- **Compatibilidade:** `findByEmail` legado não pode ser removido antes de 06-04 trocar os lookups para `usuario_id`.
- **_role String:_** `Usuario.role` continua `String` nesta wave para não quebrar testes existentes; a troca para `Role` acontece em 06-03/06-04 com os testes correspondentes.
